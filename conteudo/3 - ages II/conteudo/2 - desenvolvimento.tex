\subsection{Banco de Dados Utilizado}
No banco de dados, o projeto utilizou PostgreSQL \cite{postgresql}, escolhido por ser um banco relacional robusto e adequado para representar entidades com relacionamentos claros. Diferente da minha experiência na AGES I, em que eu tive pouco contato com a persistência, na AGES II precisei entender melhor como os dados se relacionavam, porque o filtro de estudos e o cadastro de pacientes dependiam diretamente dessas informações.

As principais entidades eram \textit{Paciente}, \textit{Medico}, \textit{Area}, \textit{Estudo}, \textit{Criterio}, \textit{CriterioEstudo} e \textit{Resposta}. A entidade \textit{Paciente} armazenava os dados necessários para a triagem; \textit{Medico} representava o profissional que utilizaria a plataforma; \textit{Area} organizava as subáreas dos estudos; \textit{Estudo} concentrava as informações dos ensaios clínicos; \textit{Criterio} guardava as perguntas ou condições avaliadas; \textit{CriterioEstudo} fazia a relação entre um estudo e seus critérios, indicando resposta esperada e se o critério era opcional; e \textit{Resposta} registrava a resposta de um paciente para determinado critério.

\subsection{Arquitetura Utilizada}
No backend, utilizamos a Arquitetura Hexagonal, que foi um modelo
de design de software que dividiu o sistema em três partes principais:
domínio, aplicação e adaptadores. O domínio ficou como o coração do sistema, onde estavam as regras de negócio e entidades
importantes; a aplicação coordenava as ações do sistema e lidava com interações entre o
domínio e o mundo externo; e os adaptadores conectavam o sistema ao mundo externo,
permitindo interações sem que o domínio precisasse saber dos detalhes técnicos.
No frontend, utilizamos o núcleo/core e seus submódulos, como core/domain para
definir as entidades principais da aplicação, como usuários e médicos. O
core/useCases foi essencial para dividir a lógica de negócios em casos de uso
comuns e específicos para diferentes tipos de usuários, enquanto o
adapters/presenter nos ajudou a adaptar os dados da lógica de negócios para a
interface do usuário. Os frameworks/ui foram vitais para organizar os componentes e
páginas da interface do usuário, enquanto os frameworks/services facilitaram a
comunicação com APIs externas. Por fim, os utils foram úteis para funções utilitárias,
como autenticação e verificação do tipo de usuário

\subsection{Tecnologias Utilizadas}
No \textit{backend}, utilizamos Java 21 \cite{java} com Spring Boot \cite{springboot}, além de JUnit para testes. Essa escolha foi feita porque boa parte do grupo já tinha familiaridade com Java, o que ajudaria na produtividade e na qualidade das entregas. O PostgreSQL foi utilizado como banco de dados relacional para armazenar as entidades principais do sistema, trazendo robustez.

No \textit{frontend}, utilizamos React \cite{react} com TypeScript \cite{typescript} e Next.js \cite{nextjs}. Também usamos Material \ac{ui} \cite{materialui} para acelerar a construção de componentes visuais e manter uma interface mais consistente. Durante as integrações, utilizei o Postman \cite{postman} para testar \ac{api}s antes de conectar as funcionalidades nas telas. Na sprint final, também tive contato com Docker \cite{docker} e com o fluxo de autenticação, o que ampliou bastante minha visão sobre como uma aplicação web funciona além da parte visual.
